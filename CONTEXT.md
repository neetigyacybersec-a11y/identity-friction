# CONTEXT

Identity Friction — signal triage for Microsoft Entra ID telemetry.

A defensive identity-security platform. It ingests Microsoft Entra ID authentication and audit
telemetry, finds identity attack patterns with deterministic rules, asks JEV (System One) for a
fast structured judgement about each candidate, then asks a small LLM (System Two) to explain the
candidate to a human analyst.

The whole project exists to hold one line steady:

> A **detected signal** is not a **confirmed attack**.

Every term below is load-bearing. Code and tests use these words, not synonyms.

## The vocabulary

### Telemetry

**event** — one row of telemetry from Entra ID. Either a sign-in log entry or an audit log entry.
An event is data. It asserts nothing.

**raw event** — the original JSON exactly as Microsoft Graph returned it. Stored unmodified
alongside the normalized form. The raw event is the audit trail: when normalization is wrong, the
raw event is how you prove it.

**normalized event** — a raw event mapped onto the project's internal event shape
(`app/models/event.py`). One shape for both sources, so detectors never branch on "is this
Graph or is this demo". Normalization drops nothing that a detector might need; unknown fields
survive in the raw payload.

**data origin** — where an event came from: `synthetic` (generated by
`scripts/generate_demo_data.py`) or `live_tenant` (fetched from a real Entra tenant). Every
normalized event carries this. The dashboard badges it. A demo screenshot and a production
screenshot must never be confusable, and this field is why.

**feature** — a number computed deterministically from a window of events: a failure count, a
unique-user count, an implied travel speed in km/h. Features are what detectors actually read.
They are pure functions with no clock, no network and no randomness, which is what makes them
testable.

**window** — a time range. A spray is "many failures inside ten minutes", so the ten minutes is
part of the definition, not a detail. Every window length is a configured threshold.

### Detection

**detection** — a deterministic rule that inspects features and fires or does not. A detection
never calls a model, never touches the network, and never changes its answer for the same input.
Four exist: password spray, MFA fatigue, geographically anomalous authentication, suspicious
OAuth consent.

**threshold** — a configured number a detection compares against. Thresholds live in
`app/config.py`, never inline in detector code, because every one of them encodes a judgement
about what is normal and that judgement is meant to be argued with.

**signal** — evidence that something matched. A spray signal is "12 failures, 7 users, one IP,
9 minutes". A signal is a reason to look, not a finding.

**candidate** — the output of a detection that fired. A candidate carries the signal, the features
that produced it, and the events that triggered it. A candidate is *not* an incident. It is a
request for a decision.

**detected signal** — the honest ceiling of this system. It can say an activity pattern is
consistent with a known identity attack technique. It cannot say an attack happened.

### Decision

**decision** — a model's structured judgement about a candidate. Produced by the JEV adapter,
normalized into `app/models/decision.py` regardless of which backend produced it.

**attack type** — a label from a small closed set: `benign`, `password_spray`, `mfa_fatigue`,
`impossible_travel`, `oauth_abuse`, `account_compromise`, `unknown`. The set is deliberately
short. A taxonomy of thirty classes would be thirty classes nobody could calibrate against.

**severity** — an integer 1–10 expressing how much analyst attention a candidate deserves. It is
not a CVSS score and is not comparable across incidents. It answers "how fast should a human
look at this", nothing more.

**confidence** — how sure the decision engine is. Calibrated confidence is *not* truth. The
project treats it as a routing signal only, never as evidence. See ADR-0002.

**confidence band** — confidence mapped onto three outcomes, which is what actually drives
behaviour:

| Band | Range | What happens |
| --- | --- | --- |
| `high` | at or above `JEV_HIGH_CONFIDENCE` | accept the classification as-is |
| `medium` | at or above `JEV_MEDIUM_CONFIDENCE` | accept it, but send the incident to the LLM for a second read |
| `low` | below `JEV_MEDIUM_CONFIDENCE` | mark `needs_analyst_review`; do not act on the classification |

A floor plus a per-stakes threshold, following TypeSafe's documented confidence-routing pattern.
Low confidence is not an error state. It is the system being honest.

**confirmed attack** — a conclusion supported by evidence this project does not have. Nothing in
this system produces one, and no field stores one. The gap between signal and confirmation is
closed by a human analyst, out of band.

### Incident

**incident** — a group of related candidates plus the events behind them, formed by the
correlation engine. Grouping keys: user, source IP, application, attack type, and a time window.

**timeline** — the incident's events in timestamp order. The timeline is the artifact an analyst
reads first, because attack chains are read in sequence: denied, denied, denied, accepted, consent
granted.

### Response

**investigation report** — the System Two output. A human-readable summary of a candidate: what
happened, which evidence supports it, which MITRE techniques it resembles, what to check next,
what to do about it, and what it cannot tell you. The last field, `limitations`, is mandatory and
not optional decoration.

**graceful degradation** — every model-backed layer is optional at runtime. If JEV is unreachable
the deterministic detection result is still produced and still shown. If the LLM is unreachable
the incident still exists with its JEV decision. Neither failure may lose a detection.

## What this system does not claim

- It does not detect token theft. The telemetry shows token and session *anomalies*, so the
  finding is named "suspicious token or session activity". See ADR-0002.
- It does not confirm attacks. It produces signals, candidates, decisions and incidents.
- It is not production-ready and makes no SOC-replacement claim.
- Geographically anomalous authentication is a heuristic, not proof. VPNs, proxies, mobile
  networks and corporate egress all produce it harmlessly.

## Constraints worth remembering before adding code

The detection path — normalize, features, detect — stays deterministic and offline. Only
`app/decision/` and `app/investigation/` may make network calls. This is what lets the detection
tests run with no credentials, no tenant and no API key.
